# InnoViewDualMonitorDriver — заметки для продолжения

Цель: свой драйвер для верхнего экрана монитора InnoView INVPM009 (USB‑чип MacroSilicon MS9132) на Mac mini M4, лучше оригинального `UsbDisplay_macOS_V3.3.1.56`.

**Статус (12.10.2026):** работает. Картинка, частичные обновления и автоповорот проверены на устройстве. Оригинальный драйвер остановлен. Материалы (логи, установщики, фото) лежат в `../tmp/` (не в git).

**17.10.2026 переименован из MSDisplayX** (было `com.newparadigma.msdisplayx`, `~/Library/Logs/MSDisplayX/msdisplayx_*.log`). Новый bundle id, поэтому разрешение «Запись экрана», автозапуск и настройки (`ConvertOnGPU`, `LoginItemOff`) выдаются и выставляются заново, а старую `~/Applications/MSDisplayX.app` нужно выключить из автозапуска и удалить. Описание для пользователей и список совместимых моделей — в `../README.md`.

## Сборка и запуск
- `./build.sh` собирает `build/InnoViewDualMonitorDriver.app` (нужны только Command Line Tools) и ставит копию в `~/Applications/InnoViewDualMonitorDriver.app`; `./build.sh run` вдобавок перезапускает работающую копию.
- То же через [just](https://github.com/casey/just) из корня репозитория (`../justfile`): `just build`, `just run`, `just clean`, `just stop` / `just start`, `just probe`, `just pattern 10 full`, `just log`; `just` без аргументов показывает список.
- Иконка: исходник `icon/AppIcon.svg` (два светящихся экрана, как у INVPM009). `build.sh` перерисовывает `build/AppIcon.icns`, только когда SVG изменился: `icon/render_iconset.m` рисует PNG через AppKit (он сам читает SVG), дальше `iconutil`. Asset catalog и Icon Composer недоступны: для них нужен `actool` из Xcode.
- Копия в `~/Applications` сама регистрируется в объектах входа (`SMAppService.mainAppService`), в меню есть переключатель «Launch at Login». Если его выключить, в defaults записывается `LoginItemOff`, и регистрация больше не повторяется. Копия из `build/` в объекты входа не регистрируется.
- Подпись ad‑hoc с `designated => identifier "com.newparadigma.innoviewdualmonitordriver"`: благодаря этому разрешение «Запись экрана» переживает пересборки. Если разрешение когда‑то выдавали сборке с другой подписью, переключатель в Настройках горит, но не действует. Лечится так: `tccutil reset ScreenCapture com.newparadigma.innoviewdualmonitordriver` → запустить → разрешить → «Выйти и открыть снова».
- Диагностика без GUI: `build/InnoViewDualMonitorDriver.app/Contents/MacOS/InnoViewDualMonitorDriver --probe` (chip id, статус, EDID; состояние не меняет) и `--pattern [сек] [full]` (цветные полосы и движущийся квадрат прямо в чип, со статистикой к/с и МБ/с).
- Журнал: `~/Library/Logs/InnoViewDualMonitorDriver/driver_*.log`, хранятся последние 20.
  Пока идёт передача, раз в 5 с пишется строка `stats:`: частота захвата и отправки, доля полных кадров, МБ/с, загрузка шины USB и время одной передачи.
- Скрытая настройка: `defaults write com.newparadigma.innoviewdualmonitordriver ExperimentalRGB -bool YES` — формат RGB888 (0x11), не проверен; он всегда конвертируется на CPU.
- Конвертация пикселей: меню «Pixel Conversion» → «GPU (Metal)» (по умолчанию) или «CPU»; переключается на ходу, выбор хранится в defaults (`ConvertOnGPU`).

## Устройство
- USB VID:PID `345f:9132`, «YC / USB Video», чип MS9132 (`A7 13 0A` по адресу 0xFF00), Video Port = 5 (HDMI).
- Интерфейсы: 0 — HID (его держит драйвер macOS, нам он не нужен), 1–2 — пустые, **3 — vendor (0xFF), bulk OUT `0x04`, max packet 16384**.
- Обычно USB 3.0 (5 Гбит/с); иногда поднимается как USB 2.0 — когда монитор отдаёт все 4 линии USB‑C под DisplayPort.
- Формат: YUV 4:2:2 (UYVY), без сжатия. Полный кадр 1920×1080 = 4 147 216 байт; по USB 3 уходит за ~12,7 мс (~326 МБ/с).
- Режимы: 1920×1080@60 = vic `0x81`, 1280×720@60 = `0x4f`.

## Протокол (сверено: Linux ms912x, дизассемблер оригинала, проверено на железе)
**USB** — напрямую через IOKit IOUSBLib (`IOUSBDeviceInterface942` / `IOUSBInterfaceInterface942`), без libusb. Устройство открывается `USBDeviceOpen`; `kIOReturnExclusiveAccess` означает, что его держит другая программа (оригинальный драйвер).

**Управление** — HID SET_REPORT/GET_REPORT через default pipe устройства, отчёт 8 байт:
- запись: `bmRequestType=0x21, bRequest=0x09, wValue=0x0300, wIndex=0`, таймаут 1000 мс
- чтение: `0xA1, 0x01, 0x0300, 0`
- чтение регистра: `[B5, addr_hi, addr_lo, 0…]` → SET_REPORT, затем GET_REPORT, значение в байте [3]
- запись регистра: `[B6, addr_hi, addr_lo, value, 0…]`
- команда: `[A6, cmd, d0..d5]`

**WaitHIDDone(addr)**: читать регистр `addr`, пока не станет 0, до 100 раз с паузой 10 мс.

| Действие | Отчёт | Ждать регистр |
|---|---|---|
| power_on(x) | `A6 07 x 02` | 0xC454 |
| video_on(x) | `A6 05 x` | 0x118D |
| transfer_mode(3) | `A6 03 03` | 0x1026 |
| video_in(w,h,fmt,sel) | `A6 01 Wh Wl Hh Hl fmt sel` (fmt 0x22 = UYVY, sel 0) | 0x1123 |
| video_out(vic,color,w,h) | `A6 02 vic color Wh Wl Hh Hl` (color = 0x00, как у оригинала) | 0x1125 |
| start_trans(x) | `A6 04 x` | — |

**screen_on(on)** для 9132 + порт 5: регистр `0xFB07`, бит `0x02`, инвертирован (read‑modify‑write).

**Регистр состояния `0x32`** (оригинал опрашивает его каждые 500 мс в `hpd_exist()`, значение хранит в `this+0x504`):
- бит `0x01` — HPD, монитор подключён. Оригинал удаляет дисплей после двух подряд нулевых чтений.
- бит `0x04` — **панель перевёрнута** (датчик ориентации монитора). Оригинал тогда переворачивает кадр программно (`UsbDisplayDevice::rotate180_yuv422`, условие `(st & 6) == 4 || == 6`), а при смене ориентации помечает оба буфера чипа для полной перерисовки (`OnFrameUpdate`).
- бит `0x40` — оригинал сохраняет в `this+0x500`, назначение неизвестно.
- Сейчас монитор отдаёт `0x05` (подключён, перевёрнут).

**Прочие регистры:** 0x31 — video port, 0xFF00..02 — chip id, EDID — 0xC000 + i побайтно (256 байт ≈ 0,8 с; у оригинала ~0,2 с).

**Порядок как у оригинала:**
1. chip id → video port → `power_on(1)` → `video_on(0)` → `screen_on(0)`
2. ждать HPD (0x32) → прочитать EDID
3. на первом кадре: `transfer_mode(3)` → `video_in(1920,1080,0x22,0)` → `video_out(0x81,0,1920,1080)` → `start_trans(1)`
4. отправить полный кадр → `screen_on(1)` → `video_on(1)`

**Кадр** — bulk OUT `0x04`, таймаут 3000 мс; одна прямоугольная область на передачу:
- заголовок 8 байт: `FF 00 | x(12 бит) y(12) | w(12) h(12)`, big‑endian, упаковано по 3 байта. При x и w, кратных 16, байты совпадают с форматом ms912x (`x/16`, `be16 y`, `w/16`, `be16 h`) — драйвер выравнивает области по 16 пикселей по горизонтали.
- далее пиксели области UYVY (`U Y0 V Y1`), BT.601 limited range
- концевик 8 байт: `FF C0 00 00 00 00 00 00`
- **Двойная буферизация чипа**: отправлять объединение новых изменений и *новых изменений предыдущей передачи* (не всей предыдущей области, иначе она растёт бесконечно). После настройки чипа и при смене ориентации первые две передачи — полные кадры.
- **Без передач экран гаснет** через несколько секунд (проверено 12.10.2026; оригинал поэтому шлёт ~2 к/с даже в простое). Драйвер в простое каждые 0,5 с повторно отправляет неизменённый участок 16×16 из текущей картинки (вместе с изменениями предыдущей передачи, если они были). Такой пульс в статистику не входит.

## Устройство драйвера (`src/`)
- `ms9132.[ch]` — протокол поверх IOKit.
- `frame.[ch]` — прямоугольники, BGRA→UYVY (`vImageConvert_ARGB8888To422CbYpCrYp8`, permuteMap {3,2,1,0}, BT.601 limited), поворот 180° (для новых областей — своя функция на NEON: конвертация и поворот за один проход; при смене ориентации — переворот UYVY в памяти), сборка пакета.
- `VirtualDisplay.m` — закрытый `CGVirtualDisplay` через `NSClassFromString`; vendor 0x6474, product 0x95AF, serial из EDID, 344×194 мм, sRGB, режимы 1920×1080 и 1280×720, без HiDPI.
- `GPUConverter.m` — конвертация на GPU: шейдер Metal компилируется при запуске из исходного текста, кадр ScreenCaptureKit отдаётся как текстура через `CVMetalTextureCache` (без копирования), результат пишется в общий буфер CPU/GPU. Формулы те же, что в NEON‑версии, результат совпадает с ней байт в байт. Если GPU‑конвертация не удалась, кадр конвертируется на CPU.
- `Capture.m` — ScreenCaptureKit: BGRA, 60 к/с, курсор, `SCStreamFrameInfoDirtyRects`.
- `Controller.m` — поток устройства (подключение, опрос раз в секунду, повторное открытие при ошибках, ожидание HPD, опрос состояния каждые 500 мс, сон и пробуждение системы, гашение при сне дисплеев) и конвейер «последний кадр»: захват конвертирует изменённые области в теневой буфер, поток устройства отправляет накопленное изменение без очереди. Виртуальный дисплей удаляется через 5 с после отключения устройства.
- Разрешение «Запись экрана»: без него ScreenCaptureKit не вызывается (каждый отказ показывает системный запрос). Запрос — один раз за запуск, дальше тихий опрос `CGPreflightScreenCaptureAccess` раз в 2 с.
  - Виртуальный дисплей существует, только пока есть разрешение (17.10.2026). Раньше он создавался сразу, оставался чёрным, и macOS открыла системный запрос и окно Настроек прямо на нём: пользователь их не видел. Теперь без разрешения дисплей не создаётся. Если ScreenCaptureKit отказывает при «да» от проверки (нужен перезапуск), дисплей удаляется, панель гаснет (`ms_stop_stream`, как при сне дисплеев; при возврате — полная перенастройка), и до перезапуска дисплей не создаётся.
  - Отозвать разрешение у работающего приложения нельзя (проверено 17.10.2026): macOS предлагает «Quit & Reopen» или «Later», и до выхода `CGPreflightScreenCaptureAccess` отвечает «да», а захват продолжает работать. После «Later» за ~3 мин с пятью переключениями (включая промежутки без разрешения от 8 с) проверка ни разу не ответила «нет». Поэтому периодической проверки отзыва нет; после перезапуска без разрешения дисплей просто не создаётся (проверено).
- `AppDelegate.m` — значок в строке меню (интерфейс на английском): состояние, скорость USB, к/с и МБ/с, предупреждение про USB 2.0, переключение 1920×1080/1280×720, автозапуск, журнал, выход.

## Производительность (12.10.2026, M4, USB 3)
- Полноэкранное видео 25 к/с: отправляются все 25 к/с полными кадрами, 104 МБ/с, шина USB занята на 33–38%, одна передача 13–15 мс, CPU процесса ~13,5% одного ядра, память ~30 МБ. В простое CPU ~0,3%.
- CPU на кадр (по `sample`): было — конвертация BGRA→UYVY ~2,3 мс, отдельный проход поворота (`vImageRotate90`) ~1 мс, копирование в пакет ~0,5 мс.
- Сделано: поворот и конвертация за один проход (своя функция на NEON, `ms_convert_rect_rot180`; с vImage совпадает с точностью до 1 в ~1% байтов). Стало 2,9 мс на кадр вместо 3,3 мс, CPU ~12,3% вместо ~13,4%, память 22 МБ вместо 30 МБ (ушёл буфер на 8 МБ).
- На CPU почти всё время уходит на чтение захваченного кадра: буфер только что записан видеокартой, процессор читает его со скоростью ~3 ГБ/с. Синтетический тест на тёплом кеше даёт в 4–5 раз меньше.
- Сделано: конвертация на GPU (Metal). На том же видео CPU процесса ~3,9% вместо ~12,3%; конвертация из профиля исчезла, осталось копирование в пакет (~0,3 мс на кадр) и обслуживание ScreenCaptureKit. Память 64 МБ вместо 22 МБ — это сам Metal. Тест на полном кадре: GPU 0,39 мс (из них 0,05 мс CPU), NEON 0,58 мс.
- Асинхронная отправка по USB при USB 3 не нужна: при 25 к/с шина занята на треть.
